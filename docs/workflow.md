# 分支与 Pull Request 流程

1. 读取远程 main 的规范和 status，记录基线 SHA 与合同版本 v1.0.0。
2. 在独立工作目录检出所属分支；先检查已有提交，不覆盖其他对话成果。
3. 在允许范围实现一个可审阅任务；不能提交真实账单、密钥、本机配置或工具缓存。
4. 提交有意义的阶段 commit，推送自己的分支。禁止推 main、强推或改写共享历史。
5. 创建 PR → main，使用模板填写范围、接口、验证与限制；需等待依赖或检查未通过时保持 Draft。
6. 主控检查接口一致性、路径所有权、数据口径和合并影响；D 提供可重复运行结果。用户/主控在聊天指出问题时，修复进同一 PR，不能仅聊天说明。
7. 主控统一解决跨模块冲突与接线，在 integration/<milestone> 形成集成 PR；完成验收后合入 main。依赖模块更新必须先进入 main，再作为下游基线。

## 合并条件

- 公共合同未被模块私自修改，或对应 contract PR 已先合并。
- ownership 检查通过；无未解决冲突；PR 验证记录准确。
- 相关 Dart/Flutter 测试在可用工具链上通过。工具缺失只能允许有明确标注的设计/骨架 PR，不能满足功能或 APK 里程碑。
- 数据库/恢复修改须 D 验证事务、精度、持久化与失败回滚；UI 修改须检查设备尺寸/大字体与空/错误状态。
- 模块作者不自行合并。负责人是同一 GitHub 身份时不能用“自我 approve”伪装独立审查，以 PR 审查记录及 D 的验证证据为准。

首次初始化空仓库由主控直接创建 main 基线是唯一 bootstrap 例外。远程 Actions 和分支保护状态分别记录，不把 YAML 文件存在当作 CI 已运行或分支保护已生效。
